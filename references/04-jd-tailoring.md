# JD 定向优化规则

> 仅当用户在第 0.5 步填入 JD 时使用。目标：判定岗位类型、抽取关键要求、
> 据此定向突出匹配的技能/工作经历/个人特性，并给出匹配说明。

## 一、判定岗位类型

对照三层类型（详见 `01-methodology.md` 第 1 节），从 JD 措辞判断：

| 类型 | JD 里的典型信号 | 简历侧重 |
|---|---|---|
| **应用层** | 需求分析、客户/预期管理、项目推进、落地、行业解决方案、B/C 端产品、运营 | 需求认知与评估、客户与项目管理、对 AI 的理解、领域落地 |
| **模型层** | 算法、模型效果、评测指标、微调/训练、数据标注、模型选型、technical | 算法与技术理解、技术选型深度、评测/调优、bad case 分析 |
| **基础设施层** | 平台、工程化、推理性能、算力、MLOps、SDK/API、系统架构 | 工程与平台能力、性能与稳定性、开发者体验 |

产出：一句话告知用户判定结果 + 依据（引用 JD 里的 1~2 个原词），并说明简历将按此侧重。
若信号混合或模糊，取占比更高的一类，并提示用户可纠正。

## 二、抽取关键要求（形成"岗位画像"）

从 JD 抽取并归为四类，逐条尽量对应 `01-methodology.md` 的能力模型：

1. **硬技能 / 工具**：如 RAG、Agent、Prompt 工程、LLM、Coze、SQL、数据分析、
   具体框架或平台。
2. **业务领域**：如智能客服、企业知识库、合同审查、电商、金融、教育等。
3. **软性特质**：如跨部门协同、向上沟通、抗压、0→1、快速学习、结果导向。
4. **高频关键词**：JD 中反复出现或放在"任职要求"前列的词（用于措辞对齐与关键词抓取）。

把画像显示给用户确认，再进入采集。

## 三、采集阶段的针对性追问

在正常字段引导之外，对画像里 JD **强调但用户尚未覆盖**的点追加一问。示例：
- JD 强调"Agent 落地" → 追问"是否有搭建/落地 Agent 或智能体的项目？"
- JD 强调"数据驱动" → 追问工作/项目结果时，强调补齐量化指标。
- JD 强调"跨部门协同" → 在工作经历里引导写出协同的具体场景。
每次只追加一问，避免打断主流程节奏。

## 四、生成阶段的定向突出

按画像对内容做**排序 + 措辞 + 显性化**三件事，且不造假：

- **排序**：匹配 JD 的自我介绍条目、工作经历、项目往前排；无关的靠后但保留。
- **措辞对齐**：在真实经历基础上，自然融入 JD 高频关键词（如 JD 说"检索增强"，
  用户写的"知识库问答"可点明"基于 RAG 的检索增强"）。**只对齐、不堆砌、不虚构。**
- **显性化特质**：JD 强调的软性特质，在自我介绍或项目"主要工作/成果"里用具体事例体现，
  而非空喊口号（如"抗压"→写高峰期如何保障项目按时上线）。
- **岗位类型侧重**：按第一节的"简历侧重"调整重点。例如投模型层，则项目的"主要工作"
  多写技术选型理由、评测方式、bad case 分析；投应用层则多写需求评估与客户/项目管理。

红线：**不得编造用户没有的经历或技能**。JD 要求而用户确实缺失的，不硬凑，放进"匹配说明"
如实提示。

## 五、匹配说明（生成简历后附上）

在 Markdown 简历末尾（或单独给出），附一段：

```
### 岗位匹配说明
- 岗位类型：{应用层/模型层/基础设施层}（依据：JD 中"…"）
- 已匹配：
  - {JD 要求 A} → 简历中「{对应的自我介绍条/经历/项目}」
  - {JD 要求 B} → 「…」
- 建议补强（JD 要求但当前较弱）：
  - {缺口项}：{可如何补充，或面试时如何解释}
```

匹配说明是给用户看的辅助信息，默认不写进最终投递版简历；用户要投递时可删除。
