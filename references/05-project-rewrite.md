# 项目经历重构规则（Mode B / Pipeline 第二阶段）

> Mode B 或 Full Pipeline 升级项目段时必读。目标：把「执行动作堆砌」重构为
> 「业务痛点抽象 — 产品判断 — 机制设计 — 价值闭环」。

## 1. 改写目标

适合 AI 产品经理 / B 端产品经理 / 大模型应用产品经理。重点体现：

1. 业务问题抽象能力
2. 产品架构设计能力
3. AI / RAG / Agent / Workflow 等能力产品化能力
4. 复杂流程治理能力
5. 质量闭环与可观测能力
6. 业务价值与系统扩展能力

不要只把句子写得更好看，要重构项目叙事逻辑。

## 2. 每个项目必须回答的 7 问

1. 面向什么业务对象？
2. 处在什么复杂场景？
3. 原始问题是什么？
4. 可抽象成哪些高密度痛点词？
5. 用了什么产品机制 / 架构方法 / 策略设计？
6. 原系统/流程从什么状态升级到什么状态？
7. 最终带来什么业务价值、系统能力或质量提升？

每条 bullet 隐含：**【问题】→【方法】→【机制】→【价值】**

## 3. 词库与痛点规范

**痛点词**：慢、乱、散、杂、断、错、漏、偏、漂、堵、弱、黑盒、不可控、不可配置、不可复用、不可观测、难归因、难回归

**价值词**：快、准、稳、全、顺、清、可控、可配、可编排、可复用、可扩展、可观测、可归因、可回归、可审计、可追溯、可回滚

**机制词**：边界治理、分层检索、标签治理、意图路由、分域 Agent、Skill 编排、动态调用、策略配置化、流程重构、任务承接、上下文管理、状态管理、强绑定生成、Bad Case 归因、评测闭环、质量回归、合规约束、人机协同、能力复用

**痛点格式**：`具体原因（凝练结果词）`
- 正确：人工创作靠经验（慢）、缺乏场景与渠道区分（同质）
- 错误：只写「慢」；或原因与结果语义重复（如「无差异化（同质）」）

术语正误用法见 `06-ai-pm-glossary.md`。

## 4. 三层颗粒度（严格边界）

| 层 | 写什么 | 不写什么 |
|---|---|---|
| **总述** | 业务对象、场景、核心痛点组合、架构升级方向、价值组合 | 具体数字、执行细节、字段枚举 |
| **Bullet** | 能力模块名、机制设计、状态升级（从→到） | 量化成果（留给成果段）；过细参数（留给面试） |
| **成果段** | 效果提升 + 能力沉淀 + 后续扩展价值（全部量化数据放这里） | — |

关键流程步骤（如「模型预判→人工复核→差异归因→修正→回归验证」）在 Bullet 中保留。

## 5. 公式

**总述（勿机械套用；多项目须句式差异化）**：
> 面向【业务对象】在【复杂场景】下的【核心痛点组合】，建设/重构【系统/平台/能力体系】。通过【关键架构/产品机制】实现【价值组合】，并形成【质量闭环/方法论资产/可扩展能力】。

**Bullet**：
> 【能力模块名称】：针对【痛点词 + 具体现象】，通过【产品机制】，将【原状态】升级为【新状态】，实现【价值/能力/质量结果】。

**能力模块命名示例**：RAG 知识边界重构、检索策略分层治理、Agent 服务路由设计、Skill 标准化沉淀、Workflow 到 Agent 架构升级、质量评测闭环、Bad Case 归因体系、策略配置化能力建设、人机协同审核机制

不要用「负责知识库建设」「参与系统设计」这类普通标题。

## 6. 禁止事项

1. 不要只写「负责、参与、完成、协助」
2. 不要堆砌 AI 术语却不说解决了什么问题
3. 不要空泛写「提升体验/效率/流程」而不说机制
4. **不要编造数据**；原文没有的百分比不要加
5. 不要把执行动作包装成战略成果
6. 不要论文式长句；要短、准、狠
7. 不要所有 bullet 同一句式
8. 不要只写技术实现，要突出产品判断与机制
9. 不要过度精简到读者不知道在讲什么
10. 不要痛点原因与结果词语义重复
11. 不要在 bullet 中放量化数据
12. 不要口语化（如「产品里有的」→「产品条款全量信息」）
13. 不要用「试点」「验证」弱化项目，除非定位确实如此

## 7. Mode B 输出步骤（逐步确认）

1. **核心矛盾提炼**（3–5 句，不复述原文）
2. **痛点词提炼**（词 + 对应业务现象）
3. **解法机制提炼**
4. **可突出产品能力**判断
5. **项目总述**：稳健版 + 锋利版；附术语解释（不入简历）；等确认
6. **逐条 Bullet**：一次一条；含改写文本、逐词能力映射表、核心信号；确认后写面试追问（中间态）
7. **成果段**：效果提升 + 能力沉淀 + 后续扩展（中间态）
8. **最终整合版（强制 STAR）**：把第 5–7 步已确认内容映射为 Mode A 同款 STAR，作为唯一可粘贴进简历的终稿：

```markdown
### {通俗项目名}（{技术栈副标题}）｜{项目时间}
- **背景**：{核心矛盾 + 痛点词（原因（结果词））+ 场景；不写具体成果数字}
- **目标**：{来自已确认总述的升级方向与价值组合；不写具体成果数字}
- **主要工作**：
  - {机制 Bullet 1：能力模块名 + 痛点→机制→状态升级→价值}
  - {机制 Bullet 2}
  - …
- **成果**：{效果提升 + 能力沉淀 + 后续扩展；量化数据集中在此}
```

映射规则：
- 第 5 步总述 → 拆入 **背景** + **目标**（不要在简历里另起「总述」段）
- 第 6 步各条 Bullet → **主要工作** 分点（可保留模块名）
- 第 7 步成果段 → **成果**
- 禁止终稿使用「总述 + 模块 Bullet 列表」版式；面试题库可继续按模块名组织

## 8. 面试追问题文件

每条 bullet 确认后写入：

```markdown
# [项目名称] — 面试追问题库

## [模块名称]

### Q1：[问题]
**考察点**：
**思路提示**：（方向，非标准答案）
```

覆盖：总述（业务理解/架构/角色边界）、每条 bullet（机制/边界 case）、成果（指标口径/归因/后续）。
